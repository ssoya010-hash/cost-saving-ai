## 1. Title — Spend less per task. Do more with AI.
🎯 오늘 이야기는 "덜 쓰기"가 아니라 "같은 돈으로 더 하기"다.

🗣 안녕하세요, FCS의 ○○○입니다. 오늘은 AI 비용 이야기를 하려고 하는데요, 아끼자는 이야기라기보다 **같은 예산으로 AI를 더 많이 쓰자**는 이야기입니다. 6월부터 조직 안에서 조금씩 해 온 실험을 오늘 GOT 레벨에서 공유드립니다.

💡 설명 팁
- 첫 문장에서 "절감 = 사용 제한"으로 오해받지 않게 "더 많이 쓰자"를 먼저 말하세요. 비용 이야기는 방어적으로 들리기 쉽습니다.
- 우측 하단 "132 graded sessions"를 한 번 언급하면 "실험 기반 발표"라는 신호가 됩니다.

➡️ "바쁘신 분들을 위해 결론부터 한 장으로 보여드리겠습니다."

## 2. TL;DR
🎯 숫자 4개와 요청 1개를 기억하게 한다.

🗣 이 한 장만 보셔도 됩니다. Claude Code는 **예상 17%**, Devin은 **예상 8%** 절감이 가능하다고 봅니다. 놀라운 점은 저희 Claude 청구액의 **72%가 '캐시에 새 컨텍스트를 쓰는 비용'** 이었다는 겁니다. 그리고 별이 수만 개인 압축 도구들은, 최신 버전으로 54세션을 다시 재 봐도 청구액을 줄이지 못했습니다. 효과가 있었던 건 **에이전트가 하는 일 자체를 줄이는 것**이었습니다. 그래서 플레이그라운드를 같이 써 보고, 채널을 만들자고 제안드립니다.

💡 설명 팁
- 4개 숫자를 **왼쪽부터 손으로 짚으며** 하나씩만 말하세요. 설명은 뒤에서 합니다.
- "72%"에서 반 박자 쉬세요. 청중 대부분이 "입력 토큰이 비싸다"고 생각하고 있어서, 여기가 첫 반전입니다.
- "0"은 "우리가 만든 도구는 AI 비용을 1원도 늘리지 않는다"로 풀어 주세요. 도구 도입 저항을 미리 줄입니다.

⚠️ 17%/8%는 반드시 "예상"이라고 말하세요.

➡️ "그럼 이게 왜 중요한지부터 보겠습니다."

## 3. Why it matters
🎯 비용 절감 = 분기 한도 안에서 더 많은 작업.

🗣 지금 AI 사용은 분기별 한도가 있고, 사람마다 다르지만 대략 **200~1000달러**입니다. 한도를 다 쓰면 다음 분기까지 AI 작업이 멈춥니다. 그래서 목표는 덜 쓰는 게 아니라 **작업당 비용을 낮춰서 같은 한도로 더 많이 끝내는 것**입니다. 그래프는 예시로 600달러 한도, 작업당 6달러를 가정했습니다. 17%를 줄이면 100개 하던 작업을 120개 할 수 있습니다.

💡 설명 팁
- **"17% 절감인데 왜 20% 증가냐"** 는 질문이 나올 수 있습니다. 1 ÷ 0.83 ≈ 1.2라서, 비용이 줄면 할 수 있는 양은 더 크게 늘어납니다. 이걸 한 줄로 짚으면 "숫자에 강한 발표자"로 보입니다.
- 청중의 실제 경험을 끌어오세요: "분기 말에 한도가 부족해서 아껴 쓰신 경험 있으시죠?"

👉 그래프의 Today(100) 막대와 −17%(120) 막대를 차례로 가리키세요.

⚠️ $600와 작업당 $6는 예시입니다. "제 경우 예시"라고 말하세요.

➡️ "이 고민이 어디서 시작됐는지 잠깐 말씀드리겠습니다."

## 4. Our journey
🎯 일회성 아이디어가 아니라 6개월간 측정으로 다져진 결과.

🗣 6월 FCS 내부 브라운백에서 AI 사용 팁을 나누면서 시작했습니다. 하반기에 분기 한도와 Devin ACU 이야기가 나오면서 "rtk나 headroom 같은 도구가 정말 비용을 줄이냐"는 질문이 생겼고, 11월에 16개 도구를 조사하고 독립 연구 6건을 모으고, 저희가 직접 132세션의 실제 청구액을 측정했습니다. 그 결과로 코칭 도구를 만들었고 오늘 여기까지 왔습니다. 강조하고 싶은 건 **들은 팁이 아니라 측정한 숫자**라는 점입니다.

➡️ "그리고 이런 고민을 저희만 하는 건 아닙니다."

## 6. Where tools act — 핵심 앵커
🎯 모든 도구를 "AI 루프의 어느 단계에 붙는가"로 보게 만든다.

🗣 AI를 쓰는 흐름을 다섯 단계로 그렸습니다. 프롬프트를 보내면 에이전트가 턴을 돌고, 도구를 호출하고, 모델이 캐시와 함께 답하고, 출력이 나옵니다. 그리고 **다음 호출 때 전체 컨텍스트를 다시 보냅니다.** 각 도구가 어느 단계에 붙는지와 실제 청구액 효과를 색으로 표시했습니다. 초록은 줄었다, 주황은 상황에 따라, 빨강은 늘 수 있다. 보시면 **행동을 바꾸는 도구는 초록, 텍스트를 압축하는 도구는 주황이나 빨강**입니다.

💡 설명 팁
- **아래쪽 되돌아가는 화살표가 핵심**입니다. "AI는 대화를 기억하는 게 아니라, 매번 처음부터 전부 다시 읽는다"고 풀어 주세요. 비개발 직군도 이해합니다.
- 비유: "회의할 때마다 지난 회의록 전체를 다시 읽고 시작하는 것. 회의록을 요약해 줘도, 요약본을 새로 복사하는 비용이 더 크면 손해."
- 도구 이름보다 **색의 패턴**을 말하세요. 도구 상세는 10~11번에서 합니다.

👉 ①→⑤ 상자를 순서대로 훑고, 되돌아가는 화살표를 따라 그리세요. 그다음 초록 3개, 빨강 2개를 차례로.

➡️ "그럼 각 도구가 무엇이고 장단점이 뭔지 하나씩 보겠습니다."

## 7. Tool catalog A — 행동을 바꾸는 도구들
🎯 도구마다 "정체(GitHub·★·형태)", 장점, 단점을 한 번에 본다.

🗣 이제 오늘 다룰 도구들을 하나씩 소개하겠습니다. 카드마다 GitHub 주소, 별 수, 형태(플러그인·스킬·MCP·훅·프록시), 장점과 단점이 있습니다. 이 장의 네 개는 에이전트의 **행동**을 바꾸는 계열입니다.
- **TokenEconomizer**(microsoft/TokenEconomizer, ★5.6K, 플러그인): 저장소마다 빌드 명령 같은 사실을 배우고, 안 쓰는 도구를 끄고, 같은 실패를 반복하면 멈추게 합니다. 579개 과제에서 18~31% 절감, 정답률도 대부분 올랐습니다. 단 개발자 본인 논문이고, 나온 지 한 달 됐고, Devin 클라우드에서는 못 씁니다.
- **Ponytail**(DietrichGebert/ponytail, ★188K, 스킬): "가장 게으른 시니어 개발자"처럼 최소한의 코드만 쓰게 합니다. JetBrains 80개 과제에서 10% 절감이 통계적으로 확인됐습니다. 대신 테스트·문서 누락이 늘었고, 가짜 복제본이 악성코드를 퍼뜨린 적이 있습니다.
- **codegraph**(colbymchenry/codegraph, ★77K, MCP): 코드 지도를 미리 만들어 두고 한 번에 찾게 합니다. 큰 저장소에선 16% 절감, 작은 저장소인 저희 실험에선 오히려 비쌌습니다.
- **serena**(oraios/serena, ★31K, MCP): 같은 계열이지만 마이크로소프트 논문에서 유일하게 비용을 늘린 도구였고, 과거 심각한 원격 실행 취약점이 있었습니다.

💡 설명 팁
- **"형태" 라벨을 꼭 읽어 주세요**(plugin · skill · MCP). 11번 구조 슬라이드에서 "형태가 어디서 돌 수 있는지를 결정한다"로 이어집니다.
- 별 수와 효과가 따로 논다는 점을 처음 보여 주는 장입니다: Ponytail은 별 188K인데 효과도 있고, serena는 별 31K에 비용 증가. "별은 인기 지표"라고 한 번 짚으세요.
- 장점·단점은 모두 읽지 말고 **각 카드에서 장점 1개, 단점 1개**만 말하세요. 나머지는 화면에 남겨 두면 됩니다.

👉 각 카드의 오른쪽 위 판정 라벨(pilot first / use as rule / large repos / avoid for cost)을 차례로.

➡️ "다음은 별이 가장 많은, 텍스트를 압축하는 도구들입니다."

## 8. Tool catalog B — 텍스트를 압축하는 도구들
🎯 인기는 최고지만 청구액은 못 줄인 도구들의 정체와 장단점.

🗣 이쪽은 별이 가장 많은 도구들입니다.
- **rtk**(rtk-ai/rtk, ★86K, 훅): git·ls 같은 셸 명령을 바꿔서 출력을 줄여 줍니다. git log 출력은 58~94% 줄고, 10ms 미만으로 빠릅니다. 하지만 청구액은 저희 측정 −5~+9%, JetBrains +7.6%였고, 출력을 손실 압축해서 정답률이 1~2점 떨어지기도 했습니다.
- **headroom**(headroomlabs-ai/headroom, ★79K, 프록시): 모델로 가는 모든 요청을 중간에서 압축합니다. JSON이나 RAG 같은 일반 API 앱에서는 강합니다. 하지만 코딩 에이전트에서는 캐시 모드 ±2%, 예전 토큰 모드 +61%였고, API 키와 프롬프트를 전부 보고, **Devin 앞에는 설치할 수 없습니다.** 왜 안 되는지는 11번에서 그림으로 보여드리겠습니다.
- **caveman**(JuliusBrussee/caveman, ★119K, 스킬+프록시): 답변을 원시인 말투처럼 짧게 만듭니다. 읽기는 편하고 품질도 같지만, 긴 세션에서 +63%였습니다.
- **context-mode**(mksglu/context-mode, ★34K, MCP+훅): 큰 출력을 로컬 저장소에 두고 검색하게 합니다. 아이디어는 좋지만 청구액 근거가 아직 없습니다.

💡 설명 팁
- **"장점은 사실이다"를 먼저 인정하세요.** 장점 칸은 모두 토큰·속도 이야기이고, 단점 칸은 모두 청구액·품질·보안 이야기입니다. 이 대비를 손으로 왼쪽→오른쪽 짚으며 보여 주면 메시지가 바로 전달됩니다.
- headroom 카드에서 **"Devin 앞에는 설치할 수 없다"를 던져 두고 11번에서 답하세요.** 청중의 궁금증을 남겨 두는 장치입니다.

👉 headroom 카드의 마지막 단점 "Cannot sit in front of Devin".

➡️ "그럼 이 도구들이 어떤 부품으로 이루어져 있는지, 한 표로 정리해 보겠습니다."

## 9. Tool anatomy — 도구의 부품과 실행 위치
🎯 형태(훅·스킬·MCP·프록시)가 "무엇을 바꾸고 어디서 도는지"를 결정한다.

🗣 도구는 네 가지 형태로 나뉩니다. **훅**은 에이전트가 명령을 실행할 때 끼어들고, **스킬**은 에이전트가 읽는 규칙이고, **MCP**는 에이전트가 부를 수 있는 새 도구이고, **프록시**는 모델로 가는 요청 자체를 가로챕니다. 표의 오른쪽 세 칸은 Claude Code, Devin CLI, Devin 클라우드에서 각각 쓸 수 있는지입니다. 훅과 프록시는 에이전트가 내 Mac에서 돌 때만 되고, Devin 클라우드에는 텍스트(AGENTS.md, 스킬)와 MCP만 들어갑니다.

💡 설명 팁
- 네 형태를 **비유**로: 훅 = 비서가 일을 시작하기 전 확인하는 체크리스트, 스킬 = 업무 매뉴얼, MCP = 새로 쥐여 준 공구, 프록시 = 모든 우편물을 중간에서 열어 보는 우체국.
- "프록시 = 우체국" 비유를 쓰면 보안 위험(API 키와 코드가 다 보임)이 자연스럽게 이해됩니다.
- 표의 Devin cloud 열에 빨간 "no"가 몰린 곳(프록시, TokenEconomizer)을 짚고, "왜 그런지는 두 장 뒤 그림으로"라고 넘기세요.

➡️ "이제 청구서가 실제로 무엇으로 이루어져 있는지 보겠습니다."

## 10. What the bill is — 1원리
🎯 청구액의 72%는 캐시 쓰기, 그리고 청구액을 만드는 4개의 원자.

🗣 청구서를 1원리로 쪼개면 **72%가 캐시 쓰기**, 출력 14%, 캐시 읽기 14%입니다. 이미 캐시에 있는 옛 컨텍스트는 0.1배라 거의 공짜입니다. 그러니 청구액을 움직이는 건 네 가지입니다: 호출 수, 새로 읽는 컨텍스트, 캐시 재작성, 출력. 특히 캐시 재작성은 제 Mac 한 대에서 **한 주 185달러 중 66달러**였습니다. 근본 원인은 하나입니다. 도구는 "응답당 토큰"을 줄이는데, 청구액은 "행동"이 결정합니다.

💡 설명 팁
- **가격표 3줄을 꼭 말로 짚으세요**: 캐시 읽기 0.1배, 캐시 쓰기 1.25~2배, 출력 5배. 이 세 숫자가 이후 모든 결론의 근거입니다.
- "캐시 재작성"은 구체 상황으로: "커피 마시고 5분 넘게 쉬었다가 같은 세션에 '계속해' 하면, 지금까지 읽은 걸 전부 비싼 값에 다시 저장합니다."
- 66달러는 **제 개인 사례**이고 벤치마크가 섞여 있다고 솔직히 말하세요. 오히려 신뢰가 올라갑니다.

👉 빨간 72% 막대 → ATOM 3 카드(빨간 테두리) 순으로.

⚠️ "5 Whys"를 길게 설명하지 마세요. 아래 한 줄 결론만 읽으면 충분합니다.

➡️ "그럼 이 차이가 왜 생기는지, Claude Code와 Devin의 구조를 그림으로 보겠습니다."

## 11. Architecture — Claude Code와 Devin의 구조 차이
🎯 "에이전트와 모델 호출이 어디서 도는가"가 쓸 수 있는 도구를 결정한다. headroom이 Devin에 안 되는 이유.

🗣 이 그림이 "왜 어떤 도구는 Claude에선 되고 Devin에선 안 되느냐"에 대한 답입니다.
위쪽 **Claude Code**는 에이전트가 **내 Mac**에서 돌고, 모델 호출도 내 Mac에서 출발해 AWS로 나갑니다. 그래서 그 길목에 headroom 같은 프록시를 끼울 수 있습니다. 설정 하나(ANTHROPIC_BASE_URL)로 "모델 주소를 내 컴퓨터의 프록시로" 바꾸면 되니까요.
아래쪽 **Devin**은 다릅니다. Devin CLI는 에이전트가 내 Mac에 있지만, 모델 호출은 **Cognition 게이트웨이**를 거쳐 나가고, 거기서 ACU가 계량됩니다. 클라우드 세션은 아예 에이전트가 **Cognition의 VM**에서 돕니다. 그 사이 어디에도 우리가 프록시를 설치할 자리가 없습니다. 그래서 **headroom은 Devin에 적용할 수 없습니다.**
정리하면: 프록시는 Claude Code에서만, 훅과 플러그인은 에이전트가 내 Mac에 있을 때(Claude Code, Devin CLI)만, 텍스트 규칙과 MCP는 저장소와 함께 따라가니 어디서나 됩니다.

💡 설명 팁
- **점선 상자 = 우리가 통제할 수 있는 범위**라고 먼저 말하세요. 위쪽은 거의 다 우리 영역, 아래쪽은 오른쪽 큰 상자가 Cognition 영역입니다.
- headroom 질문에 대한 **한 문장 답**을 만들어 두세요: "headroom은 모델로 가는 우편물을 중간에서 여는 우체국인데, Devin의 우편물은 우리 동네 우체국을 지나가지 않습니다."
- TokenEconomizer가 Devin에서 안 되는 이유도 같은 그림으로: Claude Code 플러그인 형태이고 내부적으로 `claude` 명령을 호출하기 때문입니다.
- 비개발 청중이 많으면 ANTHROPIC_BASE_URL은 "모델 주소 설정"이라고만 말하세요.

👉 위 레인: Claude Code → (화살표) → headroom proxy → AWS. 아래 레인: 빨간 ✗ 문장을 손가락으로 따라 읽기.

⚠️ "Devin이 나쁘다"로 들리지 않게 하세요. "Devin은 관리형 서비스라 그 부분을 Cognition이 대신 운영한다"가 정확합니다.

➡️ "이 구조 차이를 과금·측정·레버까지 한 표로 비교해 보겠습니다."

## 12. Claude Code vs Devin — 비교표
🎯 같은 습관이 통하지만 계량기와 레버가 다르다.

🗣 표로 정리하면 이렇습니다. Claude Code는 토큰으로, Devin CLI는 토큰을 ACU로 환산해서, Devin 클라우드는 토큰에 VM·컴퓨팅까지 섞어서 과금합니다. 단가는 Claude Opus 4.6 정가 기준 입력 100만 토큰 5달러, Devin은 ACU당 0.4달러입니다. 셋 다 프롬프트 캐시가 있고, Claude는 기본 5분입니다. 측정은 Claude는 cost-coach가 로컬 기록으로 자동, Devin은 `/session-stats`나 Session Insights 값을 기록합니다. 가장 큰 레버는 Claude는 캐시 습관과 TokenEconomizer, Devin 클라우드는 fast 모드 끄기와 대화 왕복 줄이기입니다. 예상 절감은 Claude 약 17%, Devin CLI 약 10%, Devin 클라우드 약 8%입니다.

💡 설명 팁
- 행이 많으니 **세 줄만** 강조하세요: "과금 단위", "넣을 수 있는 것", "가장 큰 레버".
- Devin 사용자가 많다면 **fast 모드 4배**를 꼭 강조하세요. 도구 설치 없이 설정 하나로 가장 크게 줄일 수 있는 항목입니다.
- "Devin CLI는 사실상 Claude Code와 같은 방식으로 아낄 수 있다"는 점이 실무자에게 가장 유용한 정보입니다.

➡️ "그럼 도구들이 광고한 숫자와 실제 숫자를 나란히 놓아 보겠습니다."

## 13. Advertised vs measured
🎯 광고(◇)와 실측(●) 사이의 큰 간극.

🗣 다이아몬드가 광고한 절감률, 점이 실제 청구액 변화입니다. 위쪽 행동형 도구들은 점이 왼쪽, 절감 쪽에 있습니다. 아래쪽 압축 도구들은 광고는 −60~−90%인데 점은 0 근처이거나 오른쪽, 비용 증가 쪽입니다. headroom 예전 모드는 61%, caveman 최신 버전은 긴 세션에서 63%까지 늘었습니다.

💡 설명 팁
- **읽는 법부터** 10초 설명하세요: "왼쪽일수록 돈이 줄고, 오른쪽은 늘어난 것. 세로선이 0%."
- rtk 줄처럼 점이 넓게 퍼진 것은 "연구마다 결과가 흔들린다 = 믿을 만한 효과가 없다"는 뜻이라고 해석해 주세요.
- 광고 숫자가 거짓말은 아니라는 점도 짚으세요: "응답 하나의 압축률로는 맞는 숫자입니다. 다만 청구액이 아닙니다."

👉 rtk 줄의 다이아몬드(−90%)와 점들(0 근처) 사이 거리를 손으로 벌려 보이세요.

➡️ "'버전이 옛날 것 아니냐'는 반론이 있어서, 저희가 직접 다시 재 봤습니다."

## 14. Our re-test (v2) — 우리 재검증
🎯 반론을 미리 막고, 누구나 검증 가능한 데이터라는 신뢰.

🗣 1차 측정 후 "도구 버전이 옛날 것 아니냐, 시나리오가 불리했던 것 아니냐"는 지적이 있어서, **최신 버전**으로, 각 도구에 **유리하게 설계한 시나리오 3개**를 3번씩, **54세션**을 다시 돌렸습니다. 판단 기준은 실행 **전에** 정했습니다. 결과는 어떤 압축 도구도 기준을 통과하지 못했고, caveman은 긴 세션에서 63% 비쌌습니다. 도구는 분명히 작동했습니다. rtk는 명령 81개 중 46개를 바꿨고, headroom은 요청 170개 중 152개를 압축했습니다. 그런데도 청구액은 그대로였습니다.

💡 설명 팁
- **"판단 기준을 실행 전에 정했다"를 강조**하세요. 결과를 보고 기준을 맞춘 게 아니라는 뜻이고, 엔지니어 청중에게 가장 설득력 있는 문장입니다.
- **"한 번만 재면 속는다"** 카드를 꼭 이야기하세요: 1회차엔 4개 도구가 11~28% 절감처럼 보였는데 3회차엔 사라졌습니다. 팀에서 "써 보니 좋더라" 같은 후기를 들었을 때 왜 조심해야 하는지 알려 줍니다.
- 시나리오는 한 줄씩: S1 테스트 5,700개 돌려 범인 커밋 찾기(셸 위주), S2 증상에서 3단계 떨어진 원인 찾기(코드 탐색), S3 1.3MB 로그 RCA(긴 컨텍스트).
- caveman이 왜 비싸졌는지: "압축해 둔 원문이 필요해서 에이전트가 세션마다 11~14번 다시 꺼내 왔다. 압축이 오히려 턴을 늘렸다."

👉 표의 빨간 칸 3개(caveman +46/+63, 조합 +45) → 오른쪽 "Why one run lies" 카드.

⚠️ n=3이라 **15% 미만 차이는 구분할 수 없다**는 한계를 먼저 말하면 공격받지 않습니다. Ponytail은 1회 측정이라 "판단 보류"입니다.

➡️ "그럼 효과가 있었던 쪽을 자세히 보겠습니다."

## 15. Deep dive A — 행동을 바꾸는 도구
🎯 효과와 한계를 함께 보여줘 과장 없이 신뢰를 얻는다.

🗣 실제 절감 근거가 있는 쪽은 에이전트의 행동을 줄이는 도구들입니다. **TokenEconomizer**는 Microsoft Research가 만든 것으로, 실패 루프를 끊고 안 쓰는 도구를 정리합니다. 579개 과제에서 18~31% 절감, 정답률도 대부분 올랐습니다. 단 개발자 본인 논문이고 Devin에서는 못 씁니다. **Ponytail**은 "가장 작은 변경부터"라는 규칙입니다. JetBrains 80개 과제에서 10% 절감, 통계적으로 유의했습니다. 저희는 1회만 재서 아직 판단 보류이고, 테스트·문서 누락이 늘었다는 외부 평가가 있어 **플러그인 대신 규칙만** 쓰기를 권합니다. **codegraph**는 큰 저장소에서 16% 절감이었지만, 저희 작은 저장소 실험에서는 오히려 비쌌습니다.

💡 설명 팁
- 각 카드 상단의 **파란 라벨(②③⑤)을 6번 지도와 연결**하세요: "TokenEconomizer는 지도의 ②, 에이전트 턴 단계입니다."
- TokenEconomizer는 구체 예시로: "빌드 명령을 매번 헤매며 찾던 걸 한 번 배우면 다음부터 바로 씁니다. 같은 실패를 세 번 반복하면 멈추게 합니다."
- codegraph는 "큰 저장소에서 긴 탐색"이라는 **조건**을 강조하세요. 작은 저장소에선 도구 설명서 자체가 매 호출 비용입니다.

⚠️ "추천"이 아니라 "파일럿 후보"라고 말하세요.

➡️ "반대로, 별은 많은데 효과가 없었던 도구들입니다."

## 16. Deep dive B — 압축 도구
🎯 "인기 = 효과"라는 오해를 깬다.

🗣 **headroom**은 예전 토큰 모드에서 캐시를 깨서 61% 비싸졌고, 지금 기본값인 캐시 모드는 ±2%로 효과가 없습니다. API 키와 코드도 봅니다. **rtk**는 최신 버전도 −5~+9%로 효과가 없었고, 외부 1,740회 실험에서는 정답률이 1~2점 떨어졌습니다. 출력을 손실 압축해서 에이전트가 재시도하기 때문입니다. **caveman**은 최신 버전에서 긴 세션 +63%였습니다. 한 줄로 정리하면, **이미 싼 걸 줄이거나 턴을 늘립니다.**

💡 설명 팁
- rtk 실패 사례를 구체적으로: "`git diff | grep '^+'`가 원래 59줄인데 rtk를 거치면 0줄이 됩니다. 에이전트는 결과가 없으니 다시 시도하고, 그게 돈입니다."
- headroom은 **보안 이야기로 연결**하세요: "프록시라 회사 API 키와 코드가 전부 지나갑니다."
- 아래 callout의 "도구는 실제로 작동했다"를 꼭 읽으세요. "설정을 잘못한 것 아니냐"는 반론을 막습니다.

⚠️ 도구를 비난하지 마세요. "캐시가 있는 우리 환경에서는 돈이 안 줄었다"로 말하세요.

➡️ "설치하기 전에 꼭 보셔야 할 표가 있습니다."

## 17. Limitations & security
🎯 보안 위험을 분명히 하고 정책 3줄을 제안한다.

🗣 가장 큰 위험은 프록시입니다. API 키와 코드 전체를 봅니다. 과거 심각한 취약점이 있었던 도구, 악성 복제본이 돈 도구, 기본값으로 데이터를 외부로 보내는 도구도 있습니다. 그래서 정책 세 가지를 제안드립니다: **회사 코드 앞에 프록시 금지, 텔레메트리 끄기, 공식 저장소 고정 버전만.**

💡 설명 팁
- **Ponytail 악성 복제본 사례**를 짧게 이야기하면 강렬합니다: "인기 플러그인의 가짜 복사본이 마켓플레이스에 올라와 윈도우 악성코드를 배포했습니다."
- 보안팀이 청중에 있다면 정책 3줄에 대해 "보안팀과 같이 다듬고 싶다"고 열어 두세요.
- 표는 다 읽지 말고 빨간 High 3줄만 읽으세요.

➡️ "그럼 결국 우리는 무엇을 해야 할까요?"

## 18. Usage patterns — 결론
🎯 설치 없이 오늘부터 할 수 있는 습관 6개.

🗣 결론은 도구보다 습관입니다. 쉬고 돌아오면 큰 세션을 이어가지 말고 새 세션으로. 세션 중에 설정 파일 고치지 않기. "ok"만 보내지 말고 다음 지시까지 한 번에. 필요한 파일과 범위만 읽게 하기. 가장 작은 변경부터, 단 테스트와 문서는 유지. 수정 두 번, 실패 세 번이면 끊고 다시. **가장 싼 절감은 우리가 그만두는 것들입니다.** 그리고 cost-coach가 정확히 이 순간들에 알려줍니다.

💡 설명 팁
- 6개를 다 설명하지 말고 **가장 공감 가는 2개만** 예시로 풀어 주세요.
  - "ok만 보내기": "'ㅇㅇ', '계속해' 한 마디에도 에이전트는 지금까지의 대화 전체를 다시 읽습니다."
  - "새 세션으로": "점심 먹고 와서 오전 세션에 '이어서 해줘' 하면, 그 세션 전체를 비싼 값에 다시 씁니다. 요약 한 줄 들고 새로 시작하세요."
- 각 카드 위의 회색 라벨(REBUILDS/CALLS/…)이 10번의 원자와 연결된다고 한 번만 말하세요.
- 청중에게 "오늘 하나만 바꾼다면 1번"이라고 하나를 골라 주면 실천율이 올라갑니다.

➡️ "이걸 다 하면 얼마나 아낄 수 있을까요?"

## 19. Expected savings
🎯 기대 효과를 범위로, 그리고 "추정"임을 분명히.

🗣 먼저 분명히 말씀드리면, 이건 **측정 결과가 아니라 근거 기반 추정**입니다. Claude는 0~31% 사이, 예상 17%. Devin CLI는 예상 10%, Devin 클라우드는 ACU에 VM 비용이 섞여 있어 예상 8%입니다. 분기 600달러 기준이면 17%는 123달러어치, 약 20개 작업을 더 할 수 있는 양입니다. 선결제 계약이라 당장 청구서가 줄기보다는 **소진 속도가 늦어지고 갱신 규모가 줄어드는** 형태로 나타납니다.

💡 설명 팁
- **막대는 범위, 점은 예상값**이라고 읽는 법을 먼저 말하세요.
- "왜 Devin이 작냐"는 질문을 미리 답하세요: "Devin 클라우드 ACU에는 VM과 컴퓨팅 비용이 섞여 있어서 토큰을 줄여도 일부만 줄어듭니다."
- 계산 방식(1 − Π × 0.7)은 묻기 전엔 말하지 마세요. 질문이 오면 "도구 효과가 겹치는 부분을 30% 깎았다"로 답합니다.

⚠️ 경영진 앞에서는 낙관치(−31%)가 아니라 **예상치**를 기억하게 하세요.

➡️ "직접 해 보실 수 있도록 저장소를 준비했습니다."

# Q&A 답지

### Q1. rtk, headroom은 GitHub 스타가 수만 개인데 왜 효과가 없다고 하나요?
스타는 확산 지표지 절감 지표가 아닙니다. 이 도구들이 광고하는 60~99%는 **도구 응답 하나의 압축률**입니다.
실제 청구액은 캐시 때문에 다르게 움직입니다. 입력의 90%가 이미 0.1배 가격의 캐시 읽기라서 줄여도 효과가 작고,
headroom처럼 예전 대화를 다시 쓰면 캐시가 깨져 2배 가격으로 재작성됩니다. JetBrains(rtk +7.6%), Quesma(1,740회, ±5%),
Codepointer(실세션 6억 토큰, 세 도구 합쳐 3.7%), 저희 A/B(headroom +61%)가 모두 같은 방향입니다. (부록 A1)

### Q1-1. 도구 버전이 옛날 것이거나, 시나리오가 도구에 불리했던 것 아닌가요?
그 지적 때문에 재검증(v2)을 했습니다. 최신 버전(rtk 1.2.0, codegraph 1.6.2, headroom 0.44, caveman 4.1.0)을
각 도구 설치기가 하는 그대로 설정했고, 시나리오도 각 도구에 유리하게 설계했습니다(셸 위주 / 코드 탐색 / 긴 컨텍스트).
54세션, 판단 기준은 실행 전에 고정. 결과는 같았습니다. 데이터: `experiments/2026-11-tool-ab-v2/analysis.md`, `data/all_sessions.csv`.

### Q1-2. 측정 숫자를 믿을 수 있나요? n=3이면 적지 않나요?
청구액은 호출별 usage로 다시 계산했고, **72개 세션 모두 Claude Code가 직접 보고한 비용과 일치**합니다.
n=3이라 15% 미만 차이는 구분하기 어렵다는 한계는 문서에 적어 두었습니다. 그래서 "효과 없음"은 "15% 이상의 효과는 없다"로 읽으시면 정확합니다.
또 독립 연구 4건(JetBrains 80~86과제, Quesma 1,740회, Codepointer 6억 토큰)이 모두 같은 방향이라 결론은 견고하다고 봅니다.

### Q2. 17% 절감은 측정한 건가요, 추정인가요?
**추정**입니다. 공개 벤치마크와 저희 A/B 결과를 레버별로 곱해서 겹치는 효과를 30% 할인했습니다(1 − Π(1 − 레버) × 0.7).
그래서 0~31%라는 범위로 보여드렸고, 다음 파일럿에서 cost-coach의 전후 비교(`mark` → `compare`)로 실측할 계획입니다.

### Q3. Devin은 왜 절감 폭이 작나요?
Devin 클라우드의 ACU는 토큰만이 아니라 VM과 컴퓨팅 비용이 섞여 있습니다. 또 Cognition 서버에서 모델을 호출하기 때문에
프록시나 TokenEconomizer를 넣을 수 없습니다. 대신 Devin 자체 설정이 더 효과적입니다. fast 모드는 ACU 4배이니 기본값으로 끄고,
프롬프트 사전 점검과 ACU 예산을 쓰는 것을 권합니다. Devin CLI는 토큰이 그대로 ACU로 환산되니 Claude와 같은 습관이 통합니다. (부록 A2)

### Q3-1. headroom은 왜 Devin에 못 쓰나요? (11번 슬라이드)
headroom은 에이전트와 모델 사이에 끼는 **프록시**입니다. Claude Code는 모델 호출이 내 Mac에서 나가므로 "모델 주소"를 내 컴퓨터의 프록시로 바꿀 수 있습니다.
Devin은 CLI든 클라우드든 모델 호출이 **Cognition 게이트웨이**를 거쳐 나가고, 클라우드 세션은 에이전트 자체가 Cognition VM에서 돕니다. 우리가 프록시를 둘 자리가 없습니다.
게다가 Claude Code에서도 효과는 ±2%(캐시 모드)~+61%(토큰 모드)였고 API 키를 보기 때문에, 자리가 있더라도 권하지 않습니다.

### Q4. 캐시 재작성(rebuild)이 정확히 뭔가요? 왜 그렇게 비싸죠?
모델은 이전 대화를 캐시에 저장해 두고 다음 호출에서 0.1배 가격으로 다시 읽습니다. 그런데 일정 시간(보통 5분) 쉬거나,
세션 중에 CLAUDE.md·MCP·모델 같은 앞부분 설정이 바뀌면 캐시를 못 쓰고 **전체를 1.25~2배 가격으로 다시 씁니다.**
컨텍스트가 12만 토큰이면 한 번에 약 0.75달러입니다. 제 Mac에서는 한 주 185달러 중 66달러가 여기서 나갔습니다.

### Q5. cost-coach가 오히려 AI 비용을 늘리지는 않나요?
늘리지 않습니다. hook이 **아무것도 출력하지 않아서** AI 컨텍스트에 한 글자도 들어가지 않습니다. 차단·명령 재작성도 하지 않고,
무거운 분석은 백그라운드에서 돌며, hook 실행은 약 0.15초입니다. 55개 자동 테스트와 `cost-coach doctor`로 각자 PC에서 확인할 수 있습니다. (부록 A3)

### Q6. 내 코드나 프롬프트가 밖으로 나가나요?
cost-coach는 로컬 파일만 씁니다. 프롬프트 원문은 저장하지 않고, 선택 사항인 Slack 웹훅도 요약 숫자만 보냅니다.
반면 headroom·caveman 같은 프록시형 도구는 API 키와 코드 전체를 보기 때문에 회사 코드 앞에는 쓰지 말자고 제안드립니다.

### Q7. TokenEconomizer는 개발자 본인 논문인데 믿을 수 있나요?
그래서 “파일럿 우선”으로 분류했습니다. 장점은 유일하게 **캐시를 반영한 실제 청구액**과 정답률을 통계적으로 측정한 연구라는 점이고,
Microsoft Research와 UC Berkeley 공동입니다. 단점은 아직 독립 재현이 없고, 같은 저장소의 첫 5개 작업은 학습 비용 때문에 더 비싸며,
Devin에서는 쓸 수 없다는 것입니다. 파일럿으로 직접 검증하겠습니다.

### Q8-0. Ponytail은 저희 측정에서 +29%도 나왔는데요?
네, 시나리오당 1회만 측정해서(짧은 CI 분석 +29%, 코드 탐색 +6%, 긴 RCA −6%) 아직 판단 보류입니다.
1회 측정은 ±30% 흔들릴 수 있어서 결론을 내릴 수 없습니다. 외부 근거(JetBrains 80과제 −10.3%, p=0.004)가 있으니 파일럿 후보로 두고,
3회 이상 반복 측정해서 확정하겠습니다.

### Q8. Ponytail을 쓰면 코드 품질이 떨어지지 않나요?
정답률(테스트 통과율)은 유지됐습니다. 다만 외부 평가에서 **테스트·문서 누락이 17건 → 27건으로 늘었습니다.**
그래서 플러그인 대신 “가장 작은 변경부터, 단 버그 수정에는 회귀 테스트·문서는 필수”라는 **규칙만** AGENTS.md에 넣는 방식을 권합니다.
악성 복제본이 돈 적이 있으니 설치한다면 공식 저장소에서만 받아야 합니다.

### Q9. codegraph 같은 MCP를 여러 개 같이 쓰면 더 좋지 않나요?
오히려 손해입니다. MCP 도구 정의 자체가 매 호출마다 붙는 고정 비용이라, 여러 개를 쓰면 짧은 질문에서 7~30% 비싸집니다.
큰 저장소에서 긴 탐색을 하는 경우에만 **하나만** 쓰는 걸 권합니다.

### Q10. 분기 한도는 어떻게 바뀌어야 하나요?
지금은 사람당 금액 한도인데, 장기적으로는 “작업당 비용”을 보고 한도를 설계하는 게 맞다고 봅니다.
파일럿에서 작업당 비용 데이터를 모으면, 다음 분기 한도 논의에 근거로 쓸 수 있습니다. (노스스타 슬라이드)

### Q11. 누가 이걸 운영하나요? 지속 가능한가요?
저장소와 도구는 FCS에서 시작했지만, 제안은 GOT 레벨 채널에서 **각 팀이 시도하고 결과를 PR로 남기는** 구조입니다.
도구별 폴더와 결과 템플릿이 있어 누구나 기여할 수 있고, 분기마다 도구를 재평가합니다.

### Q12. 모델을 더 싼 걸로 바꾸면 되지 않나요?
가장 큰 레버 중 하나는 맞지만, 이번 범위에서는 품질 영향 때문에 모델 변경은 제외했습니다. Devin은 Opus 4.6으로 계약돼 있기도 합니다.
같은 모델에서 습관과 도구로 줄일 수 있는 부분을 먼저 확인하자는 것이 오늘의 범위입니다.

### Q13. 측정은 어떻게 하나요? 토큰 수로 보면 안 되나요?
토큰 수가 아니라 **실제 청구액**으로 봐야 합니다. 같은 토큰이라도 캐시 읽기는 0.1배, 쓰기는 1.25~2배, 출력은 5배라서 가중치가 다릅니다.
cost-coach는 Claude Code 로컬 기록의 호출별 usage를 단가로 계산하고, Devin은 ACU를 기록해서 전후 중앙값을 비교합니다.
판단 기준은 측정 구간마다 세션 20개 이상, 10% 이상 절감, 품질 저하 없음입니다.

### Q14. 이 알림이 너무 자주 오면 방해되지 않나요?
같은 규칙은 세션당 10분에 한 번, 전체는 시간당 최대 6건, 방해금지 시간과 규칙별 끄기(`cost-coach mute`)를 지원합니다.
기준값도 실제 로그로 정했습니다(도구 호출 30회 이상은 상위 3.5% 턴). 주간 회고 시간도 `cost-coach schedule`로 바꿀 수 있습니다.

### Q15. 캐시 TTL이 Devin에도 있나요?
Devin도 프롬프트 캐시를 씁니다(과금 항목에 cache_read / cache_write가 따로 있음). 다만 유지 시간은 문서에 없어서 5분으로 가정했고,
설정(`devin_cache_ttl_s`)으로 바꿀 수 있습니다.
